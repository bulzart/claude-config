# Building the CapCut project (production agent's recipe): ONE command, one composition

`CC` = `C:/Users/Bulzart/.claude/create-clips` · `PY` = `C:/Users/Bulzart/AppData/Local/Programs/Python/Python312/python.exe` · `T` = `"$PY" "$CC/scripts/cc.py"` (run through PowerShell; each prints one JSON object on its last line) · `RUN` = the run folder · `OUT` = `RUN/60-outputs/<id>`.
The project is built by ONE command, `T capcut-build` (the user, 2026-11-13: use the CapCut composition for everything, for faster delivery). It composes the whole project in a single `capcut compile` (the clips on their real chunk files, the sound-effect lanes, the transitions and every caption text with its style: in the box look one text per word and state, in the highlight look one text per moment holding the whole line with the spoken word's colour range on the tracks `wordhl-in` and `wordhl`, in the no-box look one text per caption on the `subtitle` track),
writes what compile has no operation for (zoom keys, the background blur, the caption font and entrance, the repair, the clean-up) and reads the project back (clips, length, joins, texts, media on disk, `capcut lint`): one answer. Measured on the BLAST test video (4.5 minutes, 1,909 caption texts): 8 s for the whole build, where compose, finish and the three checks as separate commands took 25 s and four agent turns.
Never build a project clip by clip (`capcut add-video`, the MCP tools): the composition is the route for every video of both modes, shorts and long videos. The older per-tool route is `capcut-build-mcp.md`: a fallback, used only when `capcut-build` has failed with a plain error that a re-run does not fix.
`capcut-compose` (the composition alone) and `capcut-finish` (the rest alone) remain for re-running one part.

## Facts about this PC's CapCut that shape the build
- CapCut Free (no Pro: a project that uses a Pro option will not export). Installed: 9.8.0.4213 (it updated itself from 9.7 on 2026-11-16; its automatic updates are off since 2026-11-19). The measured facts in this file (the transitions, what plays, the keyframe behaviour) were taken on 9.7 and are not re-measured on 9.8; projects built from the 9.7-marked template open in 9.8 and are saved by it (the builds of 2026-11-18 carry 9.8's own save markers). CapCut and capcut-cli write refuse while CapCut runs: **CapCut must be closed** for the build. If it is open that is a blocker notice to the user, not a question: the build changes nothing and says so (exit 3).
- The chunk files are used **in place**: compose builds the draft on a 350 KB placeholder and then points every clip at its real chunk file (or blurred file). Never `capcut add-video` (it copies the media into the draft; C: has little free space).
- The draft starts from `CC/data/compose-template`, an empty draft with CapCut 9.7.0 version markers (9.8 updates them when it saves a project). capcut-cli's own `auto` would use its bundled CapCut 6.5.0 (mac) skeleton here; do not pass `--template auto`.
- Never `capcut lint --fix`, `--force-write`, `capcut_transcribe`, `capcut_add_captions`, `capcut_clear_captions`, or a save with force.
- CapCut 9.7 ignored `UNIFORM_SCALE` keyframes (not re-checked on 9.8): zoom keys are written as KFTypeScaleX with the uniform scale on. Never `capcut_add_keyframe` for a zoom.
- Chroma key and screen blend do not play; scene effects and `bg-blur` are not verified here (edit-craft.md).
- Several production agents build at once, each its own draft. `capcut compile` adds the new project to CapCut's SHARED project index (root_meta_info.json), so the build holds the machine-wide store lock around that call (the same lock file the Loupe toolkit's repair takes); a build that waits for it says nothing, it only takes a few seconds longer.
- The caption font is always the look's, named by its file, so the build looks nothing up: Luckiest Guy in the box look, Montserrat Bold (`Montserrat-Bold.otf`) in the highlight and no-box looks (the highlight never takes another font). Only an EDL that names another family (the one exception: a character the look's font cannot draw, listed by `captions` as `font_missing_glyphs`) costs a scan of the PC's fonts (about 3 s); the answer is kept in `CC/data/font-cache.json` (derived data, git-ignored). The build's `caption_font` shows the file, `house_font` and any missing characters; a missing character is a problem.

## Steps
1. **Facts**: read your brief; write the EDL (edit-craft.md); `T edl-check --run RUN --edl OUT/edl.json --make-censor`; fix until it has no warnings and every cut is clean; with the run's captions setting ON (the default; `T state --run RUN get captions`) `T captions --run RUN --resolved OUT/resolved.json` and read its answer
   (names, silent stretches, `font_missing_glyphs` and `house_font`, the size); with captions OFF skip it (it would only answer "skipped"). Re-run `captions` after every `edl-check`: the build refuses a captions.json that is older than the last edl-check (the cues would not match the cuts).
2. **Build**: `T capcut-build --run RUN --video <id>` (the project name is made for you: `12_Nov_2026_kaicenat_S03`; `--name` to choose one). Its answer:
   - `ok` and `problems` (a list of plain sentences; `ok` is true only when it is empty). A problem is a fact that disagrees with the plan: a short whose canvas is not 9:16 (a short is always 9:16, 1080x1920), the main track's clip count or end time differs from `resolved.json`, clips that do not start where the one before ends, a media file missing on disk, a `capcut lint` error, a finish step that failed, a transition compile or the plan refused.
   - `draft` (the full path) and `name`; `seconds` and `seconds_by_part` (compose, finish, read_back).
   - `compose`: `pieces`, `sfx_lanes`, `video_segments_retargeted` (equal to `pieces`), `composed_in_the_same_call` (how many transitions and caption texts went into the single `capcut compile`, `caption_check_ok`), and `extras_error_then_composed_bare` when compile refused the transitions or the captions
     (an unknown transition name, say): the clips and sound effects were then composed alone and finish wrote the rest the older way, so read its steps.
   - `finish.steps`: transitions and captions marked `composed` (already in the draft, not written twice), zoom keys (`keyed`), the blur (`blurred`), the font, the entrance on the tracks that start a caption, the repair, `cleanup` (capcut-cli's undo snapshots and `*.bak` copies are removed after a good build: they were 100 MB for one 4-minute video).
   - `read_back`: `main_clips` against `planned_pieces`, `main_end_s` against `planned_s`, `joins_not_contiguous` (0), `audio_clips` against `planned_sfx`, `text_tracks` and `texts` (equal to `captions.json -> word_box.texts` in the box look to `word_highlight.texts` (two tracks) in the highlight look, with `caption_highlight` (texts in Montserrat Bold, outlined, white, at most one yellow word each, `bad` empty: any other count is a problem) and to `lines.texts` (one per caption, one `subtitle` track) in the no-box look, minus any text cut at the video's end; 0 when captions are off), `transitions_in_draft`, `zoomed_clips`, `media_missing` (`[]`), `draft_mb`,
     `lint` (`errors` must be 0; `by_code` lists the rest: one `info:media-outside-draft` per clip is expected because the chunks are used in place, and in the word-box look many `warning:caption-too-fast` because a word's text can show for 0.1 to 0.5 s; `info` about source ranges is read, not ignored: it can mean a clip points past the end of its file).
   A `problems` entry is yours to fix (re-run the part that failed: `capcut-finish` alone on the same draft, or a new build under a new `--name`) or to report; never to ignore.
3. **Look at it** (the read-back cannot): for a short under 90 s a proxy preview, `capcut render "<draft>" --out "OUT/preview.mp4" --burn-captions`, then 3 frames with ffmpeg `-ss` on the preview. The proxy shows order, timing and captions only: not layouts, keyframes, the box look or blur
   (those are checked on the read-back and, for blur, with `cc.py censor --preview-only` and the frames around each blurred span). A long video has many pieces: the read-back is the check; no proxy of the whole hour.
   The detail commands still exist when a number looks wrong: `capcut segments "<draft>" --track video` (the clips in order, `start_us` contiguous from 0), `capcut texts "<draft>"`, `capcut lint "<draft>"`.
4. **Report**: `OUT/report.md` (a few lines each): what the video is, source spans, length, the project name and path, layouts and why, zooms, transitions, sfx (name, time, why), the blurred spans (rec range, what, region, style),
   exclamations or touchy items left in (safety.md), captions (cues, texts, the look: box, highlight or no-box; in the box look the box colour and why; the lexicon entries held for review or refused; the size, `house_font`, lexicon fixes applied; or "captions: off"), the source quality, what the user must do in CapCut (open it, check the first frame of a `fill` layout and the caption look once, export at 1080x1920 or 1920x1080, 30 fps), anything not verified;
   and `OUT/posting.md` (title, description, hashtags, chapters for a long video). Then `T state --run RUN set videos.<id>.status=built videos.<id>.project="<name>" videos.<id>.duration_s=<n>`.

## The pieces, when one has to be run alone
- `T capcut-compose --run RUN --video <id> [--name N] [--bare]`: the composition only. `--bare` leaves the transitions and the captions to `capcut-finish` (the older split; the same project comes out, checked text by text on the BLAST test video: 1,909 texts, 0 differences). It writes `OUT/composed.json` (what is in the draft), which finish reads so it writes only the rest.
- `T capcut-finish --run RUN --draft "<draft>" --video <id>`: the rest. On a draft built another way (the MCP route, `--bare`, or after the plan changed: a fingerprint of the planned texts tells) it writes the transitions and the captions itself, the older way.
- The media pool (`draft_meta_info.json -> draft_materials`) lists only files that exist: a missing one makes CapCut open the project with a "Media lost / Link media" window. A project built from capcut-cli's or the MCP's clone of a template can carry the template's media there; the composition does not.

## When something goes wrong
- The build says CapCut is running: close it, run it again (set `videos.<id>.status=ready-to-build` and stop when you cannot). It failed with a plain error (a missing media file, a refused spec, a captions file that is missing or older than the last edl-check, an EDL whose music patch is newer than the last edl-check): the error text says which; fix the cause (a wrong path in the EDL, a chunk that is not there, run `captions` again) and run it again;
  a half-made draft folder that a failed compile left is yours to remove only by its exact path (the build removes its own when it retries without the extras).
- `video_segments_retargeted` is less than `pieces`, or `big_media_copied_into_the_draft` is not empty: the draft is wrong; delete that one draft folder by its exact path and build again under a new `--name`.
- A finish step says a piece has no clip: the main track's clips do not start where the plan says; build again.
- A scale or position that looks wrong in CapCut: re-run `T layout-calc` for that source and canvas, put the numbers in the EDL's layout, re-run `edl-check` (and `captions`), build again under a new name; note it in the report.
- Never leave a half-built project that looks finished: if the build cannot be completed, the report says what is missing and `videos.<id>.status=failed`.
